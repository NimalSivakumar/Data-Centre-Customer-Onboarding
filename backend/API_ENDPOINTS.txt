Data Centre Customer Onboarding - Backend API Endpoints

Base URL:
http://127.0.0.1:8000

Protected business endpoints require Authorization: Bearer <Entra token> plus X-App-Session-ID: <active application session UUID>.
The backend binds the session to the token's stable subject and rejects it at 15 minutes without user activity, independently of Entra token expiry. Identity/site-settings/session bootstrap endpoints are Entra-only; session lifecycle endpoints validate ownership/state.
Feature migration: 202610290023 must be applied before deploying the matching backend/frontend. Existing legacy sessions require sign-in again.

Health
GET /health
Purpose: Check whether the backend is running.

Authentication
Session mutation routes require Admin/Ops/Security and update only user_session_events for start, activity, heartbeat, end and inactivity timeout. They do not duplicate events in audit_logs. The app session expires after 15 minutes of inactivity; this does not globally revoke Entra access tokens.
GET /api/v1/auth/me
Purpose: Get the current Microsoft Entra-authenticated user details.

GET /api/v1/auth/site-settings
Purpose: Return configured site_timezone and site_location to authenticated internal users. No secrets or other application settings are returned. Frontend loads these before protected pages render.

POST /api/v1/auth/sessions
Purpose: Start a user session tracking record.
Response: session_id, idle_remaining_seconds, idle_timeout_seconds (900), idle_warning_seconds (120). Binds session to stable Entra subject; initial activity is server UTC time.

POST /api/v1/auth/sessions/{session_id}/heartbeat
Purpose: Record connectivity and validate that the session remains active. Does not update last_activity_at or extend idle lifetime. Returns the same JSON session-status fields as session creation (no longer HTTP 204). Expired/unavailable sessions return 401.

POST /api/v1/auth/sessions/{session_id}/activity
Purpose: Report actual user input activity and update server-side last_activity_at on an active owned session. Cannot revive ended/expired/legacy sessions; returns 401 in those cases. Returns JSON session status. Background polling must not call this route.

POST /api/v1/auth/sessions/{session_id}/end
Purpose: End a user session tracking record.
Optional body: reason = USER_SIGNED_OUT (default) or SESSION_TIMED_OUT. Remains idempotent for an already-ended owned record.

Security Portal
Response fields: visitor name, full NIN, request number, visitor status, expected arrival/departure, customer company, equipment carried, actual check-in/check-out timestamps, plus visitor_access_id and visit_date for operations.
Other personal/contact details and security notes are not returned by these endpoints. Notes may still be submitted for security actions.
List and detail reads only expose approved requests or historical expired visits. Hidden or missing detail records return 404.

GET /api/v1/security/visitors/{visitor_access_id}

Audit Logs
GET /api/v1/audit-logs
Purpose: View audit logs with filters and pagination. Admin/Ops only.
Pagination: page (default 1), page_size (default 50, maximum 100).
Session filter: exclude_session_events defaults to true and excludes legacy user_session records from items and total. Both timeline and every export batch explicitly use true. Explicit false is reserved for authorized historical diagnostics; normal audit views/exports do not include sessions. Existing stored rows are not deleted.
Date filters: from_day and to_day as YYYY-MM-DD, inclusive calendar dates in the configured site timezone.
Existing from_date and to_date timestamp filters remain supported.
Export traversal: before_created_at (timestamp with timezone offset) and before_id (UUID), supplied together with page=1.
Results are ordered by created_at descending, then id descending. Cursor traversal avoids offset shifts from newer audit inserts.

Does data pass through the API before the database?
Yes. The system data goes through the API first. It does not go directly from the frontend/system to the database.

Flow:
Frontend/System
-> FastAPI endpoint
-> Authentication and role checks
-> Service function
-> SQLAlchemy database session
-> Database

Database connection file:
backend/app/db/session.py

API dependency that provides database sessions:
backend/app/core/dependencies.py
